# Headless Royder for agents’ worktrees

**Design proposal for headless-royder’s review · 22 November 2026**

I recommend a small **Royder primary** listening on the existing MCP port, with Rider and a dedicated headless executable registering solutions as peers. The primary can answer a new session before an engine exists. Each headless process opens one worktree’s solution and owns its engine thread, file synchronization and shutdown. I would give Royder responsibility for these processes and let the ClaudeTooling hub request a warm start when it prepares a worktree.

The first implementation decision should turn on one experiment: run the **actual Royder host and tools inside the dedicated executable**, then drive an external edit, a Royder edit and an ordinary worktree removal through that same process. The two spikes separately proved the engine lifetime and the plugin loading path. Together they justify this experiment. No combined run is assumed below.

The recommendations below are proposals. The measurements above are the other helpers’ runs, checked against their reports. The rollout and tests below have not been performed.

## 1. Routing through one MCP server

**Recommend a dedicated primary.** Keep `dotnet-analysis-and-refactoring` and the configured loopback URL (normally port 23751). Run the lightweight primary independently of Rider and engine lifetimes. Reuse Royder’s MCP protocol, routing rules, peer forwarding and `notifications/tools/list_changed`. Extract the necessary protocol/routing code into an engine-independent assembly if required. Even a primary that only routes calls should not need to load a ReSharper solution.

- **No Rider or headless hosts running.** The primary serves `initialize` and `tools/list` from a tool description manifest generated from the released tools. Compare the manifest with a live matching build in specifications. Today `Serving/ToolList.cs:14` derives the descriptions from open solutions and otherwise exposes only `list_solutions`. Without this change a fresh MCP client cannot discover the tool that would start its first host. A delegated call must still check what the selected peer actually serves. Preserve `list_solutions` JSON, the live host/build fields in `/health` and list-change notifications consumed by existing clients.
- **Who holds which port.** The primary exclusively owns the configured base port in headless-enabled mode. Each peer binds its own available loopback port, keeps the socket and announces the actual port. Use OS-assigned bound ports for new headless workers, avoiding a probe/release/rebind race. If retaining `HttpListener` requires a numbered candidate, bind-and-retry in the worker and register only after a successful bind. Current `McpShellComponent.cs:18` tries ten ports including the primary and can promote a peer when the primary disappears. Separate the base port from the worker’s listen port; a managed configuration must also suppress promotion. Port 23900 was an experiment setting.
- **Route by identity.** Verify the canonical physical worktree root for absolute paths *before* `OpenSolutions.Choose` returns its sole open solution and before a broader parent checkout can claim a nested worktree. Match a registered solution in that root first, then use the existing closest solution folder and explicit name/full path/unique segment rules. Resolve each file in `filePaths` and `symbols[].filePath`. Reject conflicting targets before dispatch, especially for edits. An explicit solution can identify linked files outside its tree; a conflict with a different identifiable worktree warrants a specific error. A relative path or symbol alone carries no caller working directory over this HTTP interface. Retain the existing unambiguous open-solution shortcuts, and request an absolute path or solution selector when identity is ambiguous.
- **Duplicates and restarts.** If Rider already serves this solution, use Rider and its unsaved-document rules. If Rider opens it later, finish admitted calls on the headless worker, let it stop, and hand off new work without concurrent writers. Current registration uses only the solution path as a dictionary key and deregisters by path (`McpHttpServer.cs:503`). Add a peer-instance identity and acknowledge registration. A late disconnect or reused port must not evict a replacement or send an edit to the wrong checkout. Re-register on primary restart, validate the selected identity at dispatch, and never replay a possibly executed edit after a lost reply.

**Alternative.** Keep whichever Rider or headless worker binds first as primary, using `PrimaryServer.Register` unchanged. That is the smallest change for a test with Rider open. In production an incoming TCP request cannot start a process on an unbound port. On Magnus’s machine I would activate the small primary at login, with session startup or explicit warm start able to ensure it is running. CI can start the same primary as a job service. A client-launched stdio entry point under the same key is another viable bootstrap where installing a listener is unwelcome, but it changes transport configuration. Introduce the managed primary as an explicit deployment mode and migrate existing Rider primaries in a coordinated restart.

## 2. On-demand start and readiness

**Recommend one idempotent start operation**, used by both the router and a proposed `royder start <solution-path> [--wait]`. A first file call resolves the nearest existing parent, asks Git for the physical worktree root/admin directory, and examines solutions in *that worktree*. Reuse a recorded explicit selection for that worktree identity if still valid. Otherwise prefer a unique candidate containing the file’s project, or a sole unambiguous `.sln` or `.slnx`. Look beyond root-level solutions. Treat indistinguishable root solutions, differing configurations for the same project, and missing solutions as actionable results listing the candidates. A lightweight path heuristic can narrow the search; a tie must not silently pick alphabetical order. An absolute `solutionName` can select the file directly, including for a symbol-only call. For a non-Git CI checkout, allow an explicit solution root.

Deduplicate starts by canonical worktree identity and chosen solution. Initially allow one selected headless solution per worktree. If a second solution is explicitly selected while the first is active, report which one is active and support an explicit switch after draining it. Multiple simultaneous solutions in a worktree are an extension for a demonstrated need. Two worktrees of the same repository must always be distinct.

Return promptly with a retryable **starting** or **indexing** result naming the target. For example, “Indexing C:\worktrees\agent-2\Compze.AllProjects.slnx. Retry this call when the solution is ready.” Return it as a tool-level outcome and leave the MCP transport healthy. Do not queue the original edit for later execution. The caller retries once the worker is ready. Distinguish memory deferral, selection ambiguity and actual load failure from indexing. An additive per-target health entry can show pending state before a worker registers. Preserve existing ready-solution fields. Mark ready after project load/synchronization, a committed PSI model, an observed available/idle cache service, and usable tool registration. `Indexing.IsRunning` currently treats a missing cache component as idle. SWEA completion is separate and affects only the appropriate tools. A bounded load failure reports its reason and releases the start reservation.

**Alternative.** Have the hub explicitly preselect and start every worktree it creates. This handles ambiguous solutions well and hides a 13–49 s launch, but plain Git worktrees and CI would miss on-demand behavior. Offer prewarming alongside automatic discovery.

## 3. Idle expiry and worktree removal

**Recommend an initial ten-minute idle timeout**, adjustable after field measurements. Count actual tool activity and outstanding calls, including work still unwinding after cancellation. Health, registration and client tool-list polling must not keep a solution alive. An explicit stop rejects new calls, drains an in-flight edit, disposes the solution and shuts down its private workers. A new call during an ordinary idle shutdown can wait for the prior worker to exit and start a fresh one. A stop for removal prevents a new launch for the old worktree identity.

Watch the worktree’s **parent** for removal/rename and its Git administrative identity for changes. At notification, invalidate routing immediately, cancel outstanding work for the vanished tree and reap the process tree. Recheck identity before dispatch/write and periodically in case events are lost. A recreated directory at the same path is a new worktree. Keep the worker executable, logs, caches, pipes/records and process working directory outside the worktree. Track only child processes belonging to that worker. Avoid owning shared build servers or killing unrelated `dotnet` or MSBuild processes.

**The removal event arrives too late to release a handle that prevented removal.** A plain `git worktree remove` on a clean disposable worktree must succeed on its first attempt, even during indexing or a long query. Look specifically for open directory watcher handles, memory-mapped references/analyzers, source or generated-file streams, project/solution files, temp files and worker current directories. Check their sharing flags and whether editor-less save/rename can recreate paths after removal. Test the complete process tree and also removal during an edit, distinguishing Git’s legitimate dirty-worktree refusal from a sharing violation.

**Alternative.** The hub can call `stop` before a removal it initiates, giving an orderly drain. It cannot cover ordinary Git invocations. If a necessary engine handle prevents raw removal, first redirect/shadow-copy that particular input or change its lifetime. If that cannot work, a private shadow worktree with explicit path translation and guarded write-back is an option, with significant consistency and refactoring costs. Treat plain removal as unproved until the lock test passes.

## 4. Admission by machine memory

**Recommend one memory reader at the lifecycle owner.** The contract is the login-session pipe. Its actual Windows name is `MachineStallRecorder.LiveSamples.<sessionId>`. It sends five minutes of history at connect and then one UTF-8 JSON line per sample, normally once a second. The source-generated wire names are **`at`, `availableMB`, `physicalMB`, `committedGB`, `commitLimitGB`**. The computed percentages are omitted from the JSON. Use the sample time/offset for age and window coverage. Compute physical percent used as `100 × (1 − availableMB / physicalMB)` and commit percent as `100 × committedGB / commitLimitGB`. Null, absent or invalid totals give unknown capacity.

`WarningThresholds.Default` starts memory yellow at physical use ≥85%, red at ≥92% and blinking at ≥98%. Commit ≥90% is red even with ample physical memory. Use the owner’s threshold contract, preferably via a small shareable definition or an additive recorder field for gauge level, rather than allowing private constants to drift. No CPU, GPU, process-name or paging counters are needed to reproduce the green-memory decision. Tell tooling-owner the exact fields when adopting the contract. Evidence: `MachineStalls/Sampling/MachineSample.cs`, `Recording/RecordingsJson.cs`, `LiveSamples/LiveSamplesPipe.cs`, `Warning/WarningsOfTheMachine.cs` and `Warning/WarningThresholds.cs` under ClaudeTooling’s `src`.

- **When to check.** Continuously consume samples, including the backlog. Before *every* new automatic or explicit start, evaluate recent history and the latest sample, then reserve the estimated incremental startup memory in the same admission decision. Existing ready hosts continue serving. As an initial tuning choice, require 30 s of green readings with no material gaps, a latest sample at most 5 s old, and enough headroom for starts still in progress. Multiple worktrees may start if there is room for all. Release or reconcile reservations as usage is observed, or on failure/exit. Measure private bytes of the whole worker tree and system commit across startup before settling on a reservation. The 1,272 MiB observation is a starting point for that measurement.
- **When tight.** Stop the least recently used *idle headless* worker first. Recheck a fresh sample after it and its children exit; avoid evicting more solely because historically yellow samples remain in the window. Defer with the actual physical/commit reading and reason if no idle worker is available, or capacity has yet to recover. Never count Riders as eviction candidates. No fixed host count applies while memory is plentiful.
- **No fresh pipe.** On this Windows machine reconnect for history and give a retryable “memory status unavailable” for new automatic launches if it stays unavailable. For CI/cloud, make the alternative explicit: read OS/container headroom with an operator-provided byte budget for the job, or have the job explicitly provision a worker budget. Do not apply host-wide RAM readings to a constrained container. A latest-sample-only policy is simpler but vulnerable to brief recovery and simultaneous launches; a fixed count ignores the contract and the size of the solutions.

## 5. Isolating files and settings

**Recommend three distinct owners of files.** The agent owns the worktree’s sources and build. Royder owns a per-user directory *outside* the worktree for each engine’s state. Magnus’s Rider owns its settings and caches. Give each headless host a distinct identity based on the worktree, solution and engine wave, so two checkouts with the same solution name cannot share writable state. A source edit expressly requested through Royder still writes to the real worktree.

| Files | Proposed handling and evidence |
|---|---|
| Solution/shell caches, plugin metadata, roaming data, temp and logs | Set `--caches-home`, `JET_LOCAL_APPDATA_DIR`, `JET_ROAMING_APPDATA_DIR`, `TEMP`, `TMP` and the engine’s temp/log paths in the child’s own environment. The experiments observed solution databases, shell caches, usage databases, culture/device/settings data, shadow copies and worker logs. The extension additionally expanded its package and generated JetMetadata. Pin the engine/tools installation and share its immutable binaries. Key retained caches to the worktree identity and compatible engine version; remove obsolete state following shutdown. |
| `.idea`, solution-personal settings and Magnus’s profile | Read repository-owned `.editorconfig` and solution-team `.DotSettings` as inputs. Mount any explicitly selected personal settings read-only or copy them into private state. Direct writes to private layers. A headless open must leave `.idea`, `*.DotSettings.user` and all Rider profile paths untouched. Trace the worker tree’s filesystem operations on a disposable instrumented checkout. A clean Git status misses ignored files and writes of identical content. |
| `obj`, `bin`, restore data and paths outside the worktree | The stock loader changed `Solution.UserDocs.assets.cache` under `--no-build`. For a dedicated disposable agent worktree, the simplest option is to allow its *own* build intermediates when all writable project paths are local and the agent build can coexist. This cannot supply isolation for a checkout or linked project that Rider also uses. Prefer the existing Rider for that solution. For shared checkouts, try suppressing the observed cache write with `DisablePackageAssetsCache` and supply project-specific intermediate/output/restore paths where needed. Restore and design-time evaluation must agree about `MSBuildProjectExtensionsPath`, generated imports, per-project/TFM/configuration identity and glob exclusions. A single global replacement `obj` directory can collide across projects. Verify identical references/generated code with a parallel ordinary build. |

**Tradeoff.** Start the pilot on dedicated agent worktrees with the observed `obj` behavior documented. Redirecting intermediate paths for *every* project offers stronger isolation but may alter what a project loads. A private copy with path remapping goes further and complicates navigation, source edits and concurrent changes. For the main checkout with Rider closed, offer direct loading only once traced writes and model parity satisfy separation there; otherwise report the specific limitation rather than silently evaluating it with shared writable state. Arbitrary MSBuild imports can select their own destinations, so no single switch proves all projects isolated.

## 6. Keeping one tools build

**Recommend four operations selected once when composing a request for an `IMcpSolution`.** Proposed names below describe the behavior and remain open for review. Ordinary tools keep asking for an outcome, such as a current model or a temporary text control. They do not inspect process names, probe for a Rider protocol key, or interpret a missing service as readiness.

| Proposed responsibility | Rider implementation | Headless implementation and test |
|---|---|---|
| `IWorktreeFileChanges` — bring the model up to date with changed paths | Preserve `DiskSync`’s stale/unsaved checks, safe reconciliation and `Rescans` through `RefreshPaths`. Refresh both sides of a move. | On the guarded engine thread, commit pending `IFileSystemTracker` changes, synchronize affected documents and commit PSI. Include named paths and changes elsewhere for symbol-only calls. For project membership changes, request project reload and verify observable membership. Test edits, additions, deletions, rename, linked files and restore. |
| `IEditedDocumentSaver` — persist this edit and report each failure | Preserve the pre-edit unsaved set and wait for Rider’s frontend saves, including protection against a duplicate save. | After the PSI transaction, save affected documents using the platform disk writer and confirm the expected disk text before replying. An external edit since the read, cancellation and dry-run rollback each need a defined outcome. Preserve save-before-physical-move ordering. |
| `IProjectReloader` — reload the specified projects and wait for the usable model | `ISolutionHost.ReloadProjectsAsync`, `LoadEvents`, application of the new model and cache wait. | Try the **same** `ISolutionHost` operation with the CLI executor and a readiness check appropriate to it. Use the result from a changed reference or generated file as evidence. If the composed host cannot reload in place, reopening the solution is the slower fallback. |
| `IToolTextControls` — obtain a control attached to a real source document for the lifetime of a call | For a bulb, use an existing editor or create a temporary control. For completion, create the temporary control at the requested caret. | Try a backend control with in-process frontend stubs (`UselessTextControl`); its document overload still requires a working control manager and transport root. Verify position-specific completion and an actual noninteractive bulb edit. Return a precise unsupported outcome for actions requiring a user choice. PSI-only reads should not acquire a text control or eagerly construct a saver. |

A small discriminator on the stable `IMcpSolution` contract, set by Rider or by the dedicated executable at boot, would let a **single tools-side factory** construct the appropriate implementations per request. Keep identical implementations shared. Keep the existing committed-PSI locks and engine dispatcher in both hosts; these four distinctions supply no reason for a parallel threading API.

The host retains only the solution lifetime, subscriptions, watcher state and SDK-owned components that must survive swaps. A long-lived callback can hand paths/state to a host-owned object; it must not retain delegates, tasks or exceptions from an unloaded tools build. Leave protocol-independent policy and ordinary adapter code in the collectible tools assembly. If a host-specific runtime API cannot be compiled into the common `net472` build, expose only that operation through the host contract. The same **byte-identical** host DLL in both processes lets one tools DLL and its `host.sha256` serve both. A changed host contract still costs a coordinated Rider restart; an older host continues taking the last tools build compatible with its hash. Run the existing swap/unload check after using each adapter on both hosts.

**Alternatives.** Inject four complete implementations from permanently loaded host assemblies. This removes the discriminator and makes runtime-specific dependencies easy, but moves more behavior behind the Rider restart boundary. Separate tools builds would avoid adaptation at the cost of maintaining two implementations of the tool contract. I would try the single factory first.

## 7. Who owns the processes

**Recommend Royder ownership, with the hub as an optional client.** The lightweight primary already has the routing decision, selected worktree, active requests, startup status and reason for rejecting a new call. Let it own start deduplication, admission, worker identity, eviction and shutdown together. The hub can call the same warm-start/stop operation as a shell or CI job. Keep lifecycle control local to the owning user and bind only to loopback. Run workers detached from the requesting agent, with a private control channel and verified process start/instance identity. On a primary restart it can adopt a verified surviving worker; a worker unable to reconnect within a bounded grace period exits. A lost controller must not orphan MSBuild children. A worker-owned Windows job for private helpers is worth testing, particularly across adoption.

**Hub ownership is credible on Magnus’s machine.** The hub already runs detached session hosts, rediscovers them after a publish, isolates sandboxes and supplies a versioned local API. It could own process records, cancellation and the memory reader. Royder would supply worktree selection, engine arguments, readiness and per-call activity on that API. A client discovers the hub via its announcement, uses its current bearer token, and rereads the announcement on restart. The announced port and token change at publish; the hub can also stop when idle. These are different lifetime expectations from a stable HTTP MCP endpoint. A hub-owned design would need to account for both and offer a CI implementation when the hub is absent.

A hybrid with *two* independent admission/idle policies risks duplicate launches and one owner terminating the other’s active host. If the hub proves materially better at reclaiming complete worker trees or Magnus prioritizes the existing Windows-only supervisor, delegate the **whole lifecycle decision** there, keep the MCP router in Royder, and define a small explicit lifecycle contract with the hub’s owner. No hub API change or new logon service is assumed approved in this draft.

## 8. Which engine process

**Recommend the dedicated executable** calling `CommandLineProductMain.Main` with `isLiveSession: true`, using the installed `jb` runtime and a pinned compatible wave/.NET runtime. It owns the dispatcher, solution disposable, watcher commits and exit path. The console spike demonstrated repeated semantic queries and external edit reconciliation. The extension spike demonstrated that the unchanged `net472` Royder components can load in a command-line .NET process. The most valuable next step combines those results: compose Royder’s actual shell/solution components in the live executable, register them and call them over HTTP. A package or a small bootstrap component may still be useful to discover Royder in that process.

**Keep the `jb inspectcode -x` extension as a compatibility test.** It exercises vendor package discovery/metadata generation, the real host, a matching tools build and a genuine MCP read. Its tested lifetime is a pumped callback inside a finite inspection, with a disabled tracker, an unexpected-write notification and an inspection report at exit. Owning that callback indefinitely would couple edits and shutdown to InspectCode’s reporting phase. The spike’s binary inspection also found that `jb` dispatches the verb before it loads extensions. A package alone cannot introduce `jb royder serve` by that route. Reconsider the extension as the production process if JetBrains supplies a supported live command/lifetime, or if stable discovery and dispatch in the dedicated executable prove disproportionately costly.

## Decisions that need runtime evidence

| Run in a private fixture | Observation that decides the design |
|---|---|
| Connect a fresh MCP client when no Rider or worker is open. Make the first absolute-file call, then retry after readiness. Repeat with only the wrong checkout open, two requests racing, two candidate solutions, and a mixed-worktree batch. | Tool is advertised before launch, one worker is started, no edit runs while warming, and ambiguous/wrong-tree calls cannot change a file. Restart the primary, then race old deregistration with a replacement. |
| Run the actual plugin in the dedicated process. Rename a type/file, move it across folders, apply a scoped fix, then dry-run a second change. Edit/add/delete from disk between queries, change a project reference and swap tools twice. | Next query, physical files, project membership and saved bytes agree. The previous tools builds unload. Determines which adapters can reuse stock services and whether reopening is needed. |
| From another shell, remove a clean private worktree during startup, indexing and an active read without a pre-stop. Separately exercise cancellation during a write and delete/recreate at the same path. | First ordinary removal succeeds with no sharing violation. No delayed writes, stale routes, lingering worker or child processes. Capture the path, PID and handle type for any failure. |
| Trace all filesystem writes and handles of a private worker tree, from process creation to exit, alongside an independent build. Compare the ordinary model with a run using redirected intermediates. | `.idea` and Rider/user settings receive zero writes. Classify every `obj`/external write; verify framework references and generated symbols. Determines support for a shared checkout. |
| Measure simultaneous cold starts and process-tree **peak** private bytes alongside system available/committed memory. Replay green-to-yellow, commit-red, stale pipe, missing pipe and eviction recovery against the admission logic. | Green headroom admits additional workers, active edits survive pressure, and the owner reports exactly why it deferred a launch. Determines startup reserve, history window, idle timeout and CI fallback. |
| Try a known completion at two offsets and a bulb requiring no input, then a chooser/template action. Repeat after hub or primary restart. | Identifies supported control behavior and whether hosting/adoption changes the tool result. Compare with the extension route if the dedicated process cannot compose these services. |
