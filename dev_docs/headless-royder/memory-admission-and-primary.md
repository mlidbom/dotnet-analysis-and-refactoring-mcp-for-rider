# Headless Royder round 4 — memory admission and a standalone primary

**Keep the 30-second recovery window and include commit pressure.** In the recorded part of 18 November, the two limits together identified 176 ten-second summaries under pressure. The 30-second rule would have deferred starts at 231 summary endpoints. Four summaries had green physical memory while the commit gauge was red. The window filtered short recoveries without imposing a limit on the number of hosts.

**Make the primary a small `net10.0` executable that can answer MCP discovery with zero peers.** Give it the current primary URL, registration and routing, memory admission and ownership of headless workers. Keep ReSharper, solution evaluation and execution of tools in peers. The main migration issue is the sandbox: a reachable primary with an empty solution list becomes a normal state. One existing Symbol Linker check assumes a first solution.

## 1. Memory admission

### The pipe and the reusable reader

I connected read-only to `MachineStallRecorder.LiveSamples.1`, Windows login session 1. The local Windows path is `\\.\pipe\MachineStallRecorder.LiveSamples.<sessionId>`. `MachineStalls.LiveSamples` is the namespace. The recorder uses a current-user-only, byte-mode pipe. It writes one UTF-8 JSON object followed by a newline. The client sends no request body. [Reader source](../../experiments/HeadlessMemoryAdmission/RecorderMemoryReader.cs) · [Executable probe](../../experiments/HeadlessMemoryAdmission/Program.cs)

| Wire field | Recorder meaning and use |
|---|---|
| `at` | Sample-end local timestamp with UTC offset. Use it for ordering, history coverage and freshness. Arrival time alone would mistake the initial burst for current measurements. |
| `availableMB`, `physicalMB` | Usable physical memory currently available, and total usable physical memory, in **MiB** (bytes divided by 1,048,576 and rounded to whole units). Available includes reclaimable standby memory. Physical use is `100 × (1 − availableMB / physicalMB)`. |
| `committedGB`, `commitLimitGB` | System commit charge and backing limit, in **GiB**, rounded to one decimal. Commit use is `100 × committedGB / commitLimitGB`. The limit can change as Windows manages its page file. |

The two percentages are calculated properties and are omitted from the wire format. Null properties are omitted. The live capture also saw scheduler/probe latency, CPU, page reads, disk transfer latency, GPU memory, thread/process counts, port counts, busiest/largest process groups and recorder cost. Some appear only on the process/ports sampling cycle. The prototype consumed the five fields above. Once a Royder build reads the pipe, `headless-royder` will confirm its production dependencies with the tooling owner.

**What I measured.** In eight seconds the reader received **307 samples**. Of these, 299 were timestamped before the connection announcement. The oldest was 298.74 s old on connection. Source timestamps were strictly increasing, with adjacent deltas 0.998–1.002 s (median 1.000 s). The first sample had 17,375 MiB available of 95,860 MiB usable, with 116.8/141.6 GiB committed. The last had 9,741 MiB available and 124.2/141.6 GiB committed. Evaluating just the first historical sample would have produced the wrong current admission decision. `ViewersOfTheSamples.Hand` sends the in-memory history, oldest first, then live samples. There is no end-of-history marker. A newly started recorder can return less history. Its current buffer limit for a slow viewer is 360 queued samples (five minutes plus a minute).

**Absence and restart.** The reader reports unavailable on a bounded connection timeout, EOF, a broken stream or five seconds without a complete line, and reconnects. A production caller should invalidate eligibility immediately on disconnect, start a new history generation on reconnection, ignore duplicates, and require a recent complete sample plus a contiguous 30 s window. An invalid/missing denominator is unknown capacity. During receipt of the initial burst, accumulate the timestamped history; publish eligibility only after catching up with fresh samples. Do not spend the same backlog twice.

I tested unavailable → connect → EOF → reconnect → EOF on a private test pipe. The first attempt timed out at 0.74 s; the reader then received three samples from each of two successive servers and accepted an extra JSON field. I left the live recorder running. EOF/replay on an actual recorder restart follows from its source and the tested client behavior. The process-local history is lost across a recorder restart. `SamplesFromTheRecorder.ConnectThrough` in the recorder repository also represents timeout as unavailable. The diagnostic capture and transport test are in `live.jsonl` and `reconnect.jsonl`. The final reader was also exercised with a malformed line between valid records: it invalidates continuity, reports the bad line, and continues on the same stream rather than reconnecting into the same bad history.

### Replaying 18 November 2026

**Method.** I replayed all 5,987 summaries (59,790 sampled seconds) from 07:22:03 to 23:59:59 Stockholm time. The continuous file has no earlier coverage. `SummaryOfSamples` stores minimum available memory, maximum committed memory and the **last** commit limit in each group; it omits total physical memory. All 1,516 entries I found with `physicalMB` in that day’s stall files reported **95,860 MiB**, also the total seen live. I used that denominator for the morning as an explicit same-machine inference. [Replay source](../../experiments/HeadlessMemoryAdmission/replay.py)

The replay reads `MemoryYellowPercent` (85) and `CommitRedPercent` (90) from the recorder’s `WarningThresholds.cs`. It applies the same inclusive comparisons as `WarningsOfTheMachine.MemoryGauge`. RAM turning red at 92% or blinking at 98% changes the displayed severity; admission was already closed at yellow. The physical cutoff on this machine was **14,379 MiB available or less**. At each summary endpoint, classify the whole bucket as pressured if either worst figure crossed the limit. Reopen when at least 30 elapsed seconds separate the first sample of the uninterrupted green buckets and the current endpoint. Reset history at gaps over five seconds. Seven such gaps were present; missing time counts as unknown. As a sensitivity check, counting 30 nominal samples instead would defer 222 endpoints versus 231: three ten-sample buckets usually span about 29 s between their first and last timestamps.

These are **counterfactual admission checks at recorded endpoints**. They do not count attempted starts, evictions or hosts that existed that day. A ten-second summary cannot place the crossing within its bucket. Its maximum charge and last limit can yield a ratio over 100% when they came from different samples. I have not treated such a ratio as a measured instantaneous value. At the 15 transitions between adjacent ending commit limits, substituting the preceding limit for the ending limit did not change any 90% classification. No startup reservations were simulated; there is no worker-start demand series in this log.

**Interpretation.** Thirty seconds suppresses a 10 s green interval beginning 08:11:20 and a 20 s recovery beginning 20:01:20. A 40 s green interval beginning 19:55:10 would briefly reopen admission. A 60 s rule would suppress that recovery, but add 48 deferred endpoint decisions across the day. One day with no actual launch demand cannot establish an optimal window. Keep 30 s as the initial setting and collect real launch deferrals, successful starts and post-launch pressure before lengthening it.

**Keep commit in the decision.** In the exact 08:00–09:00 and 19:00–21:00 windows the commit cutoff added no blocks beyond the RAM cutoff. Just after the morning window, buckets beginning **09:00:40, 09:00:50, 09:27:20 and 09:27:30** still had 15,398–16,151 MiB available, yet peak commit was above 90% of the ending limit. Across the day, RAM alone would defer **226** endpoints at 30 s versus **231** with both limits. The commit check catches a distinct limit at little extra observed delay. ### How I would use the decision

Keep one current-user pipe connection per everyday primary. Existing peers continue serving when admission is closed. Immediately before spawning a new engine, take one synchronized admission decision over the recent samples, reservations and new request. A second request for the same solution shares the existing start. Reserve startup **physical headroom and commit** for the engine and its private children, including MSBuild and Roslyn. Charge only the part of each reservation not already reflected in a contemporaneous system sample. Reconcile it as the tree grows and release it on readiness, failure or exit. An earlier Compze run measured 1,272 MiB private for the tree at one instant; that figure is a starting estimate, not a measured peak. Keep process-tree high-water observations for calibration. Summed working sets can double-count shared pages.

A green machine with room for outstanding and requested starts admits immediately, regardless of host count. On observed or projected shortage, evict the least recently used **idle headless** worker first, await its descendants’ exit and obtain a fresh sample. Avoid evicting further workers merely because the recovery window still contains historical yellow. Protect Rider and any in-flight tool call, including work still unwinding after timeout. If no idle worker is available, report the limiting RAM/commit figure and retry condition. Stale/missing telemetry is grounds to defer new starts on Magnus’s machine; it gives no evidence for an eviction.

**Without a recorder.** On an explicitly provisioned CI/cloud installation, take a byte allowance and leave a margin for the build/test workload. Combine it with the tightest enforceable job/container headroom, accounting for the entire engine tree. On Linux cgroup v2, examine `memory.current` against finite `memory.max` at the leaf **and constrained ancestors**, using each ancestor’s own usage for shared limits. Treat a finite `memory.high` as a pressure signal. On Windows runners, use the enclosing job memory limit where available plus system commit and available RAM. A runner that cannot measure its enclosing limit should require an explicit conservative byte budget before automatic launches. A missing or restarting recorder on Magnus’s PC must not silently switch to a permissive CI policy. Neither fallback has been exercised in this round. [Linux kernel memory controller](https://docs.kernel.org/admin-guide/cgroup-v2.html#memory) · [Windows job memory limits](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_extended_limit_information)


## 2. Proposed standalone Royder primary

### Process, endpoint and ownership

Use a per-login-user `Royder.Primary` executable targeting **`net10.0` with ASP.NET Core/Kestrel**. Both `Microsoft.NETCore.App 10.0.15` and `Microsoft.AspNetCore.App 10.0.15` are installed here. Bind exclusively to the configured loopback endpoint, default `127.0.0.1:23751`. Keep the existing MCP server key and `DOTNET_ANALYSIS_AND_REFACTORING_MCP_PORT` as the **primary endpoint override**, including in isolated sandboxes. Keep the core portable; put logon integration and the recorder pipe in the Windows adapter. On CI, run the same executable in the foreground as a job service. No Rider plugin, ReSharper SDK, Windows Desktop runtime, working solution, or `jb` toolchain is required to start the primary. Only a request that actually needs an engine needs the engine installation.

The primary owns the HTTP/SSE connections, tool catalog, peer registrations, selection and headless lifecycle. Extract protocol/selection logic that is independent of PSI into a library both sides can consume (e.g. compatible targets for the `net472` plugin and the primary). Alternatively keep the peer client codes small and share only the wire types. Keep JetBrains logging/locks, `ISolution`, `IMcpTool.Execute` and the collectible tools loader in the peer. The existing public endpoint implements a particular MCP handshake and response framing; preserve it when moving the listener. For example, `McpRequest.Initialize` negotiates 2024-11-05 and 2025-03-26, `tools/call` returns MCP text content, `GET /health` is plain JSON, and `GET /` streams `notifications/tools/list_changed`. Preserve clients that POST directly, session headers/status codes and relevant cancellation/disconnect behavior. Add contract tests at this boundary.

**Rejected alternatives.** Keeping an elected Rider primary still leaves an unbound address with no Rider. A permanently loaded `jb` engine would spend solution-host resources just to list and route tools. Owning the public port in the hub would introduce its per-publish endpoint/lifetime and a second implementation for CI. Native AOT or a standalone self-contained publish may help distribution later; a framework-dependent .NET executable is simpler to debug and deploy on this machine. Existing server code in `McpHttpServer.cs` is useful behavioral evidence; moving it wholesale would pull in `SwappableTools` and a ReSharper-bound host.

### All Rider and headless hosts become peers

| Current ownership | Proposed change |

Both hosts should still load the same host bytes and use the same `host.sha256` compatibility check. Keep routing policy, tool semantics and per-call adapters out of that restart-sensitive DLL wherever possible. Tools-only fixes can still be deployed between calls. An old Rider still capable of promotion must not compete with the new primary during cutover. Stage new artifacts first, close the old primary and legacy watchdog peers in the agreed coordinated restart, start/check the new primary, then restart Riders as peers. Roll back the matched pieces together if necessary. A legacy-only sandbox can retain its existing mode until its own cutover.

### Tool manifest and mixed builds

**Current cold-start problem.** `LocalSolution.Tools` constructs `McpTools.Of(ISolution)`; even enumerating it resolves `CodeCleanupSettingsComponent`. `ToolList.Of` takes local tools if a local solution exists, otherwise registered peer tools, injects `solutionName` into schemas and prepends `list_solutions`. With zero solutions today it exposes just that one tool. A fresh client could never discover the first file tool that should wake a worktree.

**Generate a versioned manifest from authoritative descriptors at build time.** Separate public name/description/input-schema data from the factory that binds each tool to a solution. Both the manifest generator and live registrations should use those descriptors. Keep routing-only `solutionName` decoration and the `list_solutions` meta-tool in one place. At release time produce the effective public list (currently 25 solution tools plus the meta-tool), with protocol/manifest revision, tools build identity and compatible host identity. Include the initialize instructions from the same release. CI can generate and validate this without Rider; a separate live fixture compares names, ordering, descriptions, complete schemas and routing decoration with a real peer’s `tools/list`. A hand-maintained second list will drift. Making the first live peer responsible for generating it would leave a fresh installation cold again.

Ship a known-good manifest with the primary. Install/deploy the versioned manifest beside the corresponding tools build, staging into an `.incomplete` directory and switching atomically when build, manifest and `host.sha256` are present. Keep the embedded/installed fallback and previous manifest for rollback. A packaged manifest can be verified without loading a JetBrains DLL. In development, make it part of the existing sandbox-test/deploy flow. A primary update, manifest activation and a tools-only swap can each happen independently, subject to protocol compatibility.

With zero peers the active manifest supplies discovery; `list_solutions` still reports zero solutions. With live peers preserve actual availability: use their registered descriptors, deduplicate equivalent public tools, keep a deterministic preferred schema for names shared across versions, and validate a call against its **target** peer. Advertise a cold-start descriptor if the installed eligible headless build supplies it. A manifest entry alone cannot make an older peer execute a missing tool. Notify SSE clients when the effective catalog changes, including the transition back to zero peers; never silently invent an intersection of incompatible schemas. The primary’s own release/version must remain distinct from the tools build actually served by each peer.

### Logon, sandbox and Symbol Linker

**Proposal for Magnus’s approval.** Install a per-user scheduled task at logon, under Magnus’s interactive account at ordinary privilege. Run a hidden Windows launcher/executable using a stable absolute installation path, outside every worktree. Start one instance for the configured everyday endpoint, restart it on failure with bounded delay, and write diagnostics in private local app data. No time limit that ends it during a long login; consider battery/idle task conditions explicitly. The task starts only the primary. A missing recorder must still allow MCP discovery and existing peer calls. Port conflicts identify the owner/failure and keep the old process intact. Avoid running as SYSTEM/session 0: the recorder pipe and settings belong to the login session. A sandbox or CI runner starts and stops its own primary directly with its own state/port; it never modifies the scheduled task. **No task was created or changed.**

### Acceptance tests before rollout

1. A fresh client discovers and invokes a file tool with no Rider open. The real tool list matches the manifest, zero solutions remain zero until registration, and two concurrent starts create one worker. Exercise expiry of the one-minute wait with a mutation request and verify no later mutation occurs.
2. Restart the primary with both a Rider and a headless worker registered. Check registration generations, exact-worktree routing, SSE reconnect/list changes, `/health` identity, old deregistration and port reuse. A simulated lost edit response must never produce a duplicate edit.
3. Replay memory pressure/telemetry loss alongside simultaneous starts. Compare projected headroom with measured process-tree peaks, release failed reservations and verify idle-only eviction. Repeat under a finite CI/job limit.
4. Run Royder and then the linker sandbox under the existing shared turn, including zero peers, two same-named solutions, a tools-only swap and rollback. Check the linker’s selected real solution and actual build/host hash after each transition. This round did not bind, probe or call any Royder endpoint.
